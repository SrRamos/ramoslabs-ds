**Not supported as worded.**

- **MUST-1 (comparison page).** The title and the `pages.ts` title say "RamosLabs DS, Material Design, and Tailwind CSS", and the short answer leads with "Material Web is … in maintenance mode according to its README". Every Material cell is sourced to the Material Web repository, and the ledger admits the Material 3 specification site was not read. Under a "Material Design" title, "maintenance mode" reads as a statement about Google's design system, which the sources do not support (they support it for the `@material/web` components library only). The column header says "Material (Material Web)" but the title, the short answer, the summary and the index entry do not. Correction: (1) title, `summary`, the `pages.ts` title and nav, and the `/answers/` index text say "Material Web", for example "RamosLabs DS, Material Web, and Tailwind CSS: what each one ships"; (2) the first body paragraph gains the sentence the ledger already contains: "The Material column describes Material Web (`@material/web`) only; the Material 3 specification site was not consulted, so this page makes no claim about Material Design as a whole"; (3) "Material Web is in maintenance mode according to its README" in the short answer keeps the exact README wording and adds "as of 2026-10-27". The slug may stay or move to `ramoslabs-ds-vs-material-web-vs-tailwind`; the page is not yet published, so either is fine.
- **SHOULD-1 (comparison and install pages, `tw-custom`).** Two statements go one step beyond the cited page. "Tailwind documents square-bracket arbitrary properties, which accept any CSS including variables" and the FAQ "arbitrary properties that accept `var()` values": the adding-custom-styles page says arbitrary properties let you "write completely arbitrary CSS" and shows `[--scroll-offset:56px]`; its `var()` example is the arbitrary-value shorthand `fill-(--my-brand-color)`, not a `var()` inside an arbitrary property. The DS markup `[background:var(--color-surface)]` is therefore an inference from "completely arbitrary CSS", not a quoted example, and no build measured it. Correction: word it as the page does ("square-bracket arbitrary properties take completely arbitrary CSS; Tailwind's own `var()` example is the arbitrary-value shorthand `fill-(--my-brand-color)`"), and either add a measured reference (a Tailwind v4.3 build of the three-class `div` with the emitted CSS recorded, the same method as the Vite test) or drop the markup sample from both pages and keep only the CSS-import step.
- **SHOULD-2 (comparison page, `tw-utility`).** "Tailwind is a utility-first approach" is cited to styling-with-utility-classes, which never uses the term. The Tailwind homepage does ("A utility-first CSS framework packed with classes like flex, pt-4, text-center and rotate-90"). Correction: add `tw-home` (https://tailwindcss.com/, accessed 2026-10-27) and cite it for "utility-first"; keep `tw-utility` for the single-purpose-classes and reusable-components statements.
- **SHOULD-3 (indigo page).** The title "Is RamosLabs indigo (#4f46e5) WCAG accessible?" and the summary "it meets WCAG AA for text and UI" claim more than the page measures: three contrast criteria. Correction: title "Does RamosLabs indigo (#4f46e5) meet WCAG contrast requirements?", summary "it meets the WCAG AA contrast minimums for text and UI components", and keep the body as is (the body already names the criteria).
- **SHOULD-4 (DS references `ds-install`, `ds-colors`).** Both say "source at commit 71b8bac" but link the live pages `https://design.ramoslabs.com/installation/` and `/foundations/colors/`, which can change under the citation; the ledger's pinning promise does not hold for them. ## (d) JSON-LD

Generated with the branch's own `answerJsonLd` for the four answers and checked: each page emits one `FAQPage` (`@context` schema.org, `url`, six `Question` items each with an `acceptedAnswer` of type `Answer`), and the install page adds one `HowTo` (`name`, `url`, four `HowToStep` with `position`, `name`, `text`). Every `Question.name` and `Answer.text` equals the visible `dt`/`dd` text after the same `plain()` normalisation (markers and backticks removed); every `HowToStep` equals the visible list item. No marker, backtick or HTML tag leaks into the JSON-LD; the only `<` is the literal `--md-sys-color-<token>`, which is a string, not markup. The HowTo name is rendered as the visible section heading. Google's FAQ and HowTo rich results are limited since 2023, which the search-console notes already say; the markup remains valid schema.org.

- **NICE-3.** `BaseHead.astro` serialises with plain `JSON.stringify`. Escape `<` as `<` (and `>` , `&`) in the serialiser so a future answer containing `</script>` cannot break out of the script element.

## (e) Does `docs/distribution/` publish anything by itself?

No. `README.md` is an unchecked checklist that says "nothing has been submitted anywhere" and requires owner approval per item; `server.json` is an inert file until `mcp-publisher publish` is run by hand; the Smithery, PulseMCP, skill-directory and awesome-design-systems files are paste-ready text; `SEARCH-CONSOLES.md` is instructions for the owner's logins. Outside the folder, `scripts/indexnow.mjs` (`bun run indexnow`) is a dry run by default and only sends with an explicit `--submit`; there are no GitHub workflows (`.github/` holds assets only) and the site's `package.json` has no publish script. Deploying the site publishes the pages themselves, which is the intended act.
