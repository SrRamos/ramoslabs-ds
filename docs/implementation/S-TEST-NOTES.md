# S-TEST notes

## W1-114: SSR determinism runner

Code: `packages/testing/ssr/**`. Spec: PLAN W1-114, ADR-003 "SSR-safe ids", ADR-013 PR gate.

### Design
- `runSsrDeterminism(wrapper, roots)` drives any `SsrWrapper { name, renderServer, hydrate, renderClient? }`. It knows no component; W1-316
  supplies its probe wrappers through the same interface. It returns a report (`issues`, `ok`) and never throws on a determinism failure;
  `assertDeterministic(report)` throws with every issue.
- Per root: (1) server render with `window/document/navigator/location/HTMLElement/Element/Node` hidden (`withoutDom`, restored in `finally`);
  (2) the markup goes into a container of one shared jsdom document and is hydrated by the real framework; (3) optionally a fresh client render.
  Graphs are compared server vs hydrated and server vs fresh client.
- Graph (`graph.ts`): all element ids in document order, every IDREF token (`aria-labelledby/describedby/controls/owns/flowto/details`, `headers`,
  `aria-activedescendant/errormessage`, `for`, `list`) keyed by structural path, duplicates, dangling refs.
- Cross-root (ADR-003 multiple roots): ids are unioned over the roots of one document. The same id in two roots is a `collision`; a reference that
  resolves into another root is a `cross-root reference`. Checked on the server, hydrated and client sets. Roots differ only by `idPrefix`.
- Hydration diagnostics (React `onRecoverableError` plus console.error/warn, Vue console.warn) are issues too.
- Test-only components (`components/`): one neutral tree (`tree.ts`: label, input described by hint and error, trigger controlling a panel, listbox
  with `aria-activedescendant` and keyed items using `encodeKey` edge keys) rendered by `useMachine` (React), `useSJStore` (Vue), `createHost`
  (vanilla). React and Vue ids come from `useId` with the framework-level prefix (`identifierPrefix`, `app.config.idPrefix`, so `baseId(..., '')`);
  vanilla ids come only from the injected `idFactory` (a fresh sequential factory per pass; `runtime.idPrefix` is applied by `baseId`).
- Vanilla has no server renderer: "server" mounts the spec into a detached document and serializes; "client" mounts onto that markup (enhance in
  place, attributes rewritten from the view) and, separately, onto an empty element.

### Resolved ambiguities
- React fresh client render is not comparable: `useId` is `_R_<path>_` on the server and in hydration but `_r_<global counter>_` in a client-only
  root. So the React wrapper omits `renderClient` (it is optional) and hydration is the contract. Vue and vanilla do run the fresh client pass.
- React does not patch mismatched attributes on hydration ("This won't be patched up"), so for React a nondeterministic source is caught by the
  hydration diagnostic, not by the DOM graph diff. Both signals exist; either fails the run.
- The row says "vanilla run uses an injected idFactory": done through `HostOptions.idFactory` (R3 notes). No factory throws a clear error (tested).

### Seeded violations (all fail)
Shared counter and random id sources for each of React, Vue and vanilla; roots sharing an `idPrefix` for each adapter (collision).

### Shared-file changes (outside `ssr/**`)
- `packages/testing/package.json`: devDependencies `jsdom 26.1.0`, `@types/jsdom`, `react`/`react-dom` 19.3.1 (+types), `vue` 3.5.39 and the four
  workspace packages (`core`, `react`, `vue`, `vanilla`; turbo then builds them before `test`, the wrappers import their `dist` via `/runtime`).
- `packages/testing/vitest.config.ts`: `include` gains `ssr/**/*.test.ts` (the package's other tests are JS).
- `bun.lock` regenerated by `bun install`.
